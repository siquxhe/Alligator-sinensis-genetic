## 4. P1-1：Perspective 的摘要数字与自己的模型表差两个数量级

`11_proposal/Perspective_outline_Recording_is_not_discovery_2026-11-15.md`：

| 位置 | 说法 |
|---|---|
| 第 20 行（presubmission） | "the detection floor is ~10⁵ … under realistic assumptions for unknown viruses, **it exceeds 10⁸** particles/mL" |
| 第 38 行（abstract） | "ranges from ~10⁵ to **>10⁸**" |
| 第 148–149 行（模型表） | 乐观 4×10⁵ / 现实 known 1×10⁹ / **现实 unknown 1×10¹⁰** / 悲观 unknown **10¹⁴** |
| 第 166 行（结论句式） | 同样写 ">10⁸" |

按它自己的参数，现实 unknown 是 **10¹⁰**，悲观是 **10¹⁴**。"exceeds 10⁸" 在逻辑上成立（10¹⁰ 确实超过 10⁸），但比自算值低 2–6 个数量级。审稿人对照 Fig 2 热图会发现摘要区间与图的量程不一致。

更麻烦的是：这**恰好是这篇论文要批评的那类错误**——报一个口径不明的数，读者无法复算。

**建议**：摘要直接报模型区间 `4×10⁵–10¹⁴ particles/mL`，并注明这是情景包络而非实测 LOD。若担心数字太难看，就写 "10⁸–10¹⁰"（现实假设下），别写 ">10⁸"。**保守不等于模糊，模糊会被当成不诚实。**

## 5. P1-2：结论的适用边界没按样本基质分层

presubmission 与 abstract 都断言"多数环境目标低于检出下限（10⁶–10⁸ particles/mL）"。两个问题：

1. **这个范围没有出处。** 环境病毒丰度按基质差 4–5 个数量级：海水 10⁶–10⁷ mL⁻¹、土壤 10⁸–10⁹ g⁻¹、肠道/粪便 10⁹–10¹⁰ g⁻¹。要写这句，必须给每个数一个引用。
2. **结论只对低生物量基质成立。** 粪便样本目标丰度 10⁹–10¹⁰，高于现实 known 假设的 10⁹ 下限——也就是说，**在高生物量样本里，这个方案的灵敏度瓶颈不是丰度，而是受体覆盖与偏差**。

一篇以"界定边界"为卖点的论文，自己的边界却按基质漂移，会被直接质疑。而且这个修正**对你们有利**：它把结论从"方法不行"升级成"方法只在特定基质与特定问题下可行"，这才是 Perspective 该有的分寸。

**建议**：Fig 2 的 x 轴（或第二个子图）按基质分层标注典型丰度带；结论句改成"对低生物量环境样本不成立；对高生物量样本，限制因素由丰度转为受体覆盖与获取效率"。

## 7. P2-1：CRISPR 携带率文档有一处事实错误，且决策阈值应标注来源

`10_reports/CRISPR携带率_44MAGs_2026-11-15.md` 第 5 行："本 Windows 主机……**也没有可用的 Python 环境**"。

**实测不成立**：本机 Python 3.13.14，`python -m py_compile workflow/crispr_carriage.py` 通过，`--help` 正常输出全部参数。真正的阻塞是 **MAG FASTA（服务器）、MinCED、HMMER**，不是 Python。

为什么值得改：这行字会让下一个读文档的人直接放弃本地验证。去掉"没有 Python"，改成"缺 MAG 与 MinCED/HMMER"，其余不变。

另外第 13–15 行的决策规则（`cas_any >20%` / `<10%` / 10–20%）是**先验门槛**，不是从数据推出来的。写进 Perspective 或主项目时必须标明这是预设阈值及其理由（我推测是"能覆盖主要宿主门类"的最低要求，但没有写）。否则读者会以为是经验分布的分位点。

### 7.1 包装脚本有两处路径 bug（已在本仓库修正）

包内的 `run_crispr_carriage.sh` 不能直接放进仓库使用：

| 位置 | 包内写法 | 问题 |
|---|---|---|
| 调用脚本 | `python3 "$HERE/05_crispr_carriage.py"` | `05_` 是打包时加的序号前缀，仓库里叫 `crispr_carriage.py` |
| 默认 META | `"${META:-$HERE/06_mag_final_annotated.tsv}"` | `$HERE` 是脚本所在目录；仓库里元数据在 `07_mag/` |

已按仓库布局修正为 `workflow/run_crispr_carriage.sh`，并加三项：`PYTHON` 可覆盖（Git Bash 下通常只有 `python`，没有 `python3`）、脚本存在性前置检查、HMM 缺失只告警不中断。其余逻辑未动。

### 7.2 `n_evaluable = 0` 时输出 `0/0 %`，这个数字很危险

用一条合成 MAG 在本机实跑（无 minced / hmmsearch，即工具未装的情形）：

```
metric              n_positive  n_evaluable  pct  ci95_low  ci95_high
any_crispr_array    0           0
cas1                0           0
cas_any             0           0
```

`n_evaluable = 0` 时 pct 为空，终端打印成 `0/0 %`。而文档第 5 节的决策规则（`cas_any >20%` / `<10%`）没有一句要求 `n_evaluable > 0`——于是"工具没装成"会被读成"阳性率为 0"，进而触发"降级 spacer 路线"这个不可逆的决策。

一篇通篇批评"分母不写清"的论文，关键表却输出 `0/0 %`，这是最容易被反手一刀的地方。

**建议**：`n_evaluable == 0` 时 pct 直接写 `NA`；文档第 5 节加一条前置条件"先确认 `n_evaluable > 0`，否则结果不可解释"。

## 8. 结案报告：结构正确，两处措辞可再收紧

`10_reports/结案报告_工程菌诱饵方案_2026-11-14.md` 是这批文档里质量最高的一份。**A/B/C 三断言分离**（第 48–60 行）和**"它被期望回答 vs 它实际能回答"对照表**（第 37–45 行）是全文骨架，这个拆法经得起追问：A 是工程问题、B 是机制问题、C 是价值判断，强度递减且证据类型不同，不能互相顶替。

2. **"C 不成立"宜加限定**：改成"在现有成本与偏差结构下不成立"。报告自己在第 4.3 节也说了"什么条件下它可以被救活"，绝对化的"不成立"与这一节冲突。

引用方面：三个锚点题名均在 PubMed 命中，`EcRec 1 donor/10⁶ recording cells` 的口径（细胞锚点、非噬菌体 LOD）在起草包里被反复强调，这一点做得比多数引用该文的二手文献都准确。
