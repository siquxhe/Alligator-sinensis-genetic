## 1. 需求从哪来：六处真实卡点

以下每条都是这两天真实发生的事，不是设想。写法是：当时怎么了 → 代价 → 所以要什么 → 怎么算过。

### 卡点 1｜事实核查只能一条条搜，错在成稿后才暴露

**当时**：核三篇文档时，连续抓到四处事实错误——HRR 那篇被我当成预印本（其实是 Cell Reports Methods 2025）；iPHoP 的 5/5 被写成分母 19；cargo 两套口径（33 条 vs 77 条）混用；47.4% 这个数换个参考库就失效。

**代价**：每一处都是"猜一个关键词 → 搜索结果里挑三篇 → 打开 PDF 找那句话 → 记下来"。单点半小时起步，且只有在我主动怀疑时才会去查。

**要什么**：给一句论断，返回 3–5 条证据片段（原文句子 + 出处 + 年份 + 支持/矛盾/无关），我在一分钟内能判断这句能不能写进正文。

**算过**：预置 12 条有已知答案的论断（其中 4 条就是我犯过的错），Top-5 内命中正确出处的 ≥ 10/12；返回的引文必须能在原文中逐字回查（程序校验，不靠模型自觉）。

### 卡点 2｜149 条元数据，0 个 PDF

**当时**：昨天把 `Microbiome_Reptile_Immune.ris` 导入本机 Zotero，149 条进了 "Microbiomics" 分类；`storage/` 是空的。

**代价**：现在能看到的只有标题、作者、年份。方法细节、样本量、结论强度全在 PDF 里，而 PDF 在出版社网站上。这等于库只建了一半。

**要什么**：自动补摘要和开放获取全文；付费墙的只留元数据 + 摘要，不越界。

**算过**：摘要覆盖率 ≥ 90%，OA 全文覆盖率 ≥ 40%（对现有 149 条实测），拿不到的列成清单交给我，不静默跳过。

> 补充事实：Europe PMC / NCBI eutils / Crossref / OpenAlex 从这台服务器全部可达（实测 200，见附录 A-5），所以"补摘要、抓 OA 全文、校验 DOI"这件事不需要任何翻墙手段。

### 卡点 3｜我搜的词和文献用的词不是同一个词

**当时**：我搜 "host read removal"，文献写 "host depletion"；我搜 "viral dark matter"，文献写 "uncultivated viral genomes"。反过来，geNomad、PHROG、vOTU 这类缩写必须精确命中，被向量化"理解"成近义词反而是灾难。

**代价**：纯关键词漏检同义表述，纯向量检索把缩写和数字糊掉。

**要什么**：BM25 和向量双路召回，RRF 融合；缩写和数字走精确匹配通道；结果里标注"这条是靠哪一路召回的"，方便我判断为什么漏。

**算过**：10 条黄金查询（我给），nDCG@10 ≥ 0.7；其中至少 3 条纯向量会漏、3 条纯 BM25 会漏，混合后都要进前五。

### 卡点 4｜元数据本身不可靠

**当时**：`refs.ris` 是我用脚本（`make_refs.py`）生成的，DOI 有拼错风险；149 条那批是出版社网站导出的，重复条目和错年份都可能存在。

**要什么**：DOI 逐条解析校验（Crossref），缺失字段用 OpenAlex 补，重复条目检测后合并且保留可追溯记录。

**算过**：现有 149 条 DOI 可解析率 ≥ 95%；合并操作 100% 有 before/after 快照，可回滚。

### 卡点 5｜CPU 一点都不能动

**当时**：i7-9700K，8 核 8 线程（无超线程）。MEGAHIT 和 geNomad 一跑就是满载，单样本 geNomad 注释 28 分钟全程吃满。之前设过 `-t 6` 降载就是为了让机器还能响应。

**要什么**：推理走核显；CPU 硬配额（systemd `CPUQuota`）；流水线在跑时自动降级为"只排队不执行"。

**算过**：流水线运行期间，并发 20 次检索/问答后，单样本耗时增幅 ≤ 10%；服务侧 p95 延迟 ≤ 空载的 2 倍。

> **必须说清的一件事**：核显不是免费的。UHD 630 没有独立显存，它和 CPU 抢的是同一套 DDR4 内存带宽（双通道理论 42.6 GB/s）。所以走核显省下的是**核心**，不是**带宽**。MEGAHIT 这类组装器对带宽也敏感，并发时两边都会变慢。方案里因此有"流水线感知降级"，不是纯靠硬件分工解决。

### 卡点 6｜这台机器会突然断电

**当时**：11-14 到 11-15 之间四次硬断电，其中四次都发生在重负载起跑后 1.5–4 分钟内，事后判断指向供电（UPS 带载能力或 PSU 老化）。

**要什么**：所有写操作幂等（重复执行不产生重复数据）；索引损坏能重建；服务挂了自动拉起；断电不丢元数据。

**算过**：`kill -9` 和直接 `reboot` 各做一次，重启后 `/health` 恢复绿灯、索引条数与断电前一致、无重复 chunk。

## 5. 选型与理由

| 层 | 选择 | 否决了什么 | 为什么 |
|---|---|---|---|
| 元数据主库 | Zotero 10.0.8 headless + Local API | Calibre、Paperless、纯文件目录 | 已有 149 条 RIS 导入、已有 MCP 封装、能导出 BibTeX、Local API 提供 `since=version` 增量 |
| 推理运行时 | llama.cpp + Vulkan 后端 | OpenVINO、Ollama、IPEX-LLM | 单二进制、支持 Vulkan 计算、GGUF 生态全；OpenVINO 需要 Intel Compute Runtime，而 Debian trixie 没有 `intel-opencl-icd` 包，补装要走不可达的 Intel 源 |
| 主模型 | Qwen3-4B-Instruct-2507 Q4_K_M（约 2.5 GB） | 7B/8B（太慢）、1.7B（抽取质量不够） | 4B 是这条带宽下的甜点；1.7B 留作快速档 |
| 嵌入模型 | bge-m3（GGUF Q8，约 600 MB） | OpenAI embedding（不能联网）、bge-small（英文文献弱） | 中英双语、8k 上下文、llama.cpp 原生支持 `/embedding` |
| 向量检索 | numpy 暴力（float32 矩阵乘） | sqlite-vec、Chroma、Qdrant | 5 万 chunk × 1024 维 = 200 MB，一次 matmul 约 50 ms，够用；少一个依赖就少一个断电损坏点。**阈值：chunk > 20 万再换 sqlite-vec** |
| 关键词检索 | SQLite FTS5 + jieba 预处理 | Elasticsearch、Meilisearch | 单文件、随库走、`bm25()` 内建；Elasticsearch 要 JVM，抢内存 |
| 服务 | FastAPI + uvicorn（单进程） | Flask、gRPC | 同步够用，`/docs` 自带接口文档 |
| 调度 | systemd timer | cron、APScheduler | 有时序依赖（等 `/mnt/work` 挂载）、有日志、有失败重试 |
| 容器 | 不用 | Docker | 机器上没有 docker，装它是纯负担 |

## 6. 性能预算

**解码速度（估算，非实测）**

| 模型 | 权重大小 | 带宽上限 | 预期实测 | 用途 |
|---|---|---|---|---|
| Qwen3-1.7B Q4 | ~1.1 GB | ~20 tok/s | 10–15 tok/s | 分类、打标 |
| Qwen3-4B Q4 | ~2.5 GB | ~9 tok/s | 5–8 tok/s | 结构化抽取、论断判定 |
| bge-m3 Q8 | ~0.6 GB | — | 10–30 段/s | 嵌入（估算区间大，必须实测） |

**夜间窗口能干什么（按 6 小时、4B @ 6 tok/s 估）**

| 任务 | 单篇耗时 | 6 小时可处理 |
|---|---|---|
| 摘要 + 结构化抽取（输出 300 token） | 50 s | ~430 篇 |
| 分块嵌入（20 块/篇） | 3–8 s | 全量 149 篇约 10–20 分钟 |
| 论断核查（12 条证据，输出 600 token） | 100 s | 按需 |

**结论**：149 篇全量首建一个夜间窗口足够；扩到 3000 篇需要 3–5 个夜间窗口，可接受。

**检索延迟目标**：BM25 < 50 ms，向量 < 200 ms，`/ask` 端到端 20–40 s（受生成速度限制，无法更快）。

## 7. 分期与 Gate

### P0｜把核显打通，并测出真实速度（半天）

> 这一期的唯一目的：确认"核显跑得动"这件事是真的。**不通过就不要往下做**，因为后面所有设计都建立在这个假设上。

1. **人工步骤（需要输一次 sudo 密码）**
   ```bash
   sudo usermod -aG render wuyanching     # 当前只有 video 组，renderD128 读不了
   sudo apt install -y libvulkan-dev glslc ninja-build sqlite3
   ```
   退出重登（新 SSH 会话）后生效。
2. **验证核显可见**
   ```bash
   vulkaninfo --summary | grep -E "deviceName|deviceType|driverName"
   # 期望：Intel(R) UHD Graphics 630 (CFL GT2) / INTEGRATED_GPU / Intel open-source Mesa driver
   ```
   现在是 `llvmpipe / PHYSICAL_DEVICE_TYPE_CPU`，报错原文见附录 A-4。
3. **拿源码**（GitHub 在服务器上不可达，走 Windows 中转）
   ```bash
   # Windows 侧：
   curl -L -o llama.cpp.tar.gz https://codeload.github.com/ggml-org/llama.cpp/tar.gz/refs/heads/master
   scp llama.cpp.tar.gz wuyanching@192.168.71.177:/mnt/work/lib/src/
   ```
   实测：Windows 侧 `codeload.github.com` 可达（200），`github.com` 不可达（超时）；实测吞吐约 35 KB/s，完整包十几 MB，预留 10 分钟。
4. **编译**
   ```bash
   tar xf llama.cpp.tar.gz && cd llama.cpp-*
   cmake -B build -DGGML_VULKAN=ON -DCMAKE_BUILD_TYPE=Release -DLLAMA_CURL=OFF
   cmake --build build -j 6 --target llama-server llama-bench

   ```
5. **下模型**（hf-mirror 可达）
   ```bash

   ```
6. **基准**
   ```bash
   ./build/bin/llama-bench -m qwen3-4b-q4km.gguf -ngl 99 -p 256 -n 64 -t 2
   ```

**Gate P0**：`tg` ≥ 5 tok/s（4B-Q4）、`pp` ≥ 60 tok/s；`--list-devices` 显示 UHD 630。
**不过怎么办**（按顺序试）：换 1.7B → 降 `-ngl` 留几层在 CPU → 只做夜间批处理（不做交互问答）→ 放弃本地生成，只保留检索。
**产出**：`P0_基准报告.md`，含 vulkaninfo 摘要、llama-bench 原始输出、决策结论。

### P1.5｜把"只有标题"变成"有摘要、有全文"（一天）

1. 摘要：Europe PMC `search?query=EXT_ID:<doi>` → `resultList`；缺失再查 Crossref。
2. OA 全文：Europe PMC `PMC<id>/fullTextXML` 拿 JATS XML（比 PDF 干净，自带章节与页码结构）；拿不到再找 `isOpenAccess=Y` 的 PDF。
3. DOI 校验：Crossref `works/<doi>`；错号用标题 + 年份做模糊匹配后人工确认。
4. 去重：DOI 相同 / 标题归一化后 Jaro-Winkler > 0.92 判重，**只合并不删除**。
5. 失败的写 `ingest_failed.tsv`：itemKey、标题、失败原因（无 OA / 无摘要 / DOI 无效）。

**Gate P1.5**：摘要覆盖 ≥ 90%，OA 全文 ≥ 40%，失败清单可读；149 条 DOI 解析率 ≥ 95%。

### P2｜索引（一天）

1. 抽取：`pdftotext -layout`（按 `\f` 切页），保留页码；扫描件走 `pdftoppm + tesseract`（弱化，能跳过就跳过）。
2. 分块：优先按章节标题切，单块 400–600 token，overlap 80，块 id = `sha256(itemKey + page + 序号)`。
3. 嵌入：`llama-server --embeddings` 批量，32 条一批；失败重试 3 次后记录跳过。
4. FTS5：文本先 jieba 空格化，`tokenize='unicode61'`；另建一张 `tokenize='trigram'` 的表兜底中文子串。
5. 增量：Zotero Local API 的 `since=<version>` 拉变更条目；`kill -9` 后靠 content hash 跳过已完成块。

**Gate P2**：10 条黄金查询 nDCG@10 ≥ 0.7；`kill -9` 后重跑产物条数不变；单条 PDF 重跑不产生重复 chunk。

4. Windows 侧：`ssh -N -L 8765:127.0.0.1:8765 wuyanching@192.168.71.177`，用 5 个真实用例验收（见 §10）。

**Gate P3**：5 个用例全部可用；无 token 请求返回 401；服务重启后 10 秒内可服务。

### P4｜自动化与护栏（一天）

1. `job-runner.timer` 每日 01:00 跑增量；流水线在跑（`pgrep -f "megahit|genomad"`）则整体跳过并记日志。

## 8. 接口契约

| 方法 | 路径 | 入参 | 返回要点 |
|---|---|---|---|
| GET | `/health` | — | `{zotero, index, llm, disk, version}` 各自 ok/degraded/down |
| GET | `/search` | `q, k=20, mode=hybrid\|bm25\|vec` | `hits[]`：itemKey、title、year、journal、page、snippet、score、召回来源 |
| POST | `/ask` | `{question, k=12, max_tokens=600}` | `answer`、`citations[]`（itemKey/page/quote/verified）、`unverified[]` |
| POST | `/claim` | `{claim, must_terms[]}` | `verdict`（support/contradict/silent/insufficient）、`evidence[]`、`coverage` |
| POST | `/ingest` | `{type: ris\|bib\|doi\|pdf, payload\|path}` | `added, skipped, duplicates, errors[]` |
| POST | `/annotate` | `{itemKeys[], fields{}, dry_run=true}` | `op_id` + diff 预览；`dry_run=false` 才写 |
| POST | `/annotate/commit` | `{op_id}` | 执行结果 + 审计 id |
| GET | `/stats` | — | items、with_abstract、with_pdf、chunks、tokens、last_run |

**约定三条**

1. 所有写操作必须是 `prepare → diff → commit` 两段，`/annotate` 默认 `dry_run=true`。
2. `citations[].quote` 必须是原文子串（去空白后比对），校验失败自动进 `unverified` 并降权，**不允许模型"意译引用"**。
3. 任何返回都带 `model` 与 `index_version`，方便回溯"这条答案是哪个版本给的"。

## 9. 写入护栏

| 规则 | 做法 |
|---|---|
| 只读优先 | 除 `/annotate` 外全部只读 |
| 批量写需人确认 | 单次 > 10 条强制 dry-run 出报告 |
| 不删只合 | 去重做 merge，原条目保留，`relations` 记录合并关系 |
| 备份先于写 | `sqlite3 .backup`（不能 `cp`，WAL 模式下会拷到半截） |
| 审计不可关 | `ops` 表 + jsonl 双写 |
| 断点安全 | 所有 job 以 content hash 为幂等键 |
| 不覆盖用户手写字段 | 模型只能写 `extra` 里约定段落和自动标签，不碰 note 正文 |

## 11. 风险与预案

| 风险 | 触发信号 | 预案 |
|---|---|---|
| 核显性能不达标 | llama-bench `tg` < 3 tok/s | 降模型 → 留层在 CPU → 只夜间批处理 → 只检索不生成 |
| Vulkan 不稳定（Gen9 老架构） | 长跑崩溃、输出乱码 | 关 `-fa`，降 `-c`，单请求串行；必要时回 CPU 4 线程夜间跑 |
| Zotero headless 起不来 | 卡向导、缺 GTK 依赖 | `ldd` 补包；`x11vnc` 接一次手动过向导；最差退"只读 sqlite"模式 |
| 断电损坏索引 | `sqlite3 PRAGMA integrity_check` 报错 | 索引可重建（保留 `index_version`）；主库有每日备份 |
| hf-mirror 限流/不可用 | 429、502 | 换 modelscope；或 Windows 侧下载后 scp |
| 摘要/全文覆盖率不达标 | `/stats` 低于阈值 | 不追求全覆盖，输出失败清单，人工补最关键的 30 篇 |
| 抽取质量差（双栏、扫描件） | 文本乱序、字符数异常少 | 记录到 `extract_failed.tsv`，不静默入库 |
| 版权 | — | 只抓 OA（Europe PMC OA 子集、bioRxiv、PMC）；付费墙只存元数据与摘要 |
